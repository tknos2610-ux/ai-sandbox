# IssueでAIに開発させたら詰まった:OpenHands×Gemini無料枠の問題編と解決編

Nov 23, 2026 · @K

## はじめに

GitHubのIssueにラベルを付けるだけで、AIが記事や簡単なアプリを作って公開してくれる仕組みを、iPhoneと無料枠だけで試しています。使っているのは、GitHub Actions上で動くAIエージェントの OpenHands と、Geminiの無料APIキーです。

この記事は、途中で出た3つの失敗を「問題編」、その直し方を「解決編」に分けて書いたものです。

- 問題編:何が起きたか(エラーメッセージとログの中身)
- 解決編:原因と、実際に試した直し方

## 問題編1:「保存できる変更がありませんでした」

Issueに「現在このIssue解決で動いているAIモデルと、代用できるモデルと性能を表にして」と書いてラベルを付けたところ、次のコメントが付きました。

> AIは作業を終えましたが、保存できる変更がありませんでした。main は変更していません。 AIの判定:解決できなかった / ファイルの変更:なし / イベント数:43

AIの判定メモには「何も変更せず、完了を宣言しただけ」とありました。これだけでは、モデルが誤ったのか、時間切れなのか、設定の問題なのか分かりませんでした。ログを見ると AI は 43 回動いているのに、結果がゼロというのが謎です。

## 問題編2:429エラー(無料枠は毎分15回)

ログにこんなエラーが出ていました。

```
geminiException - 429 RESOURCE_EXHAUSTED
Quota exceeded for metric: generate_content_free_tier_requests, limit: 15,
model: gemini-3.5-flash-lite
Generate content requests per minute limit exceeded on Free Tier.
Please retry in 49.7s.  Attempt #1
```

意味は「Geminiの無料枠で、このモデルに送れるのは1分あたり15回まで」です。OpenHandsは1つの作業でモデルを何度も呼ぶので、すぐに上限に当たります。「Attempt #1」とあるように、自動で再試行はしていましたが、待ちが重なると作業が途中で終わることがあります。

このエラーでここに初めて「使っているモデルは gemini-3.5-flash-lite」と判明しました。無料枠の数字は2026年11月時点の解説記事によると、毎分15回・1日500回です(Google AI Studioで最新を確認してください)。

## 問題編3:回答がIssueに出ない、しかREADMEに書かれた

対処して再実行しても、同じ「変更がありませんでした」が返ってきました(イベント数は23)。しかし、ログとして保存される output.jsonl を開くと、429は出ておらず、AIは最後に比較表つきの回答をちゃんと書いていました。つまり「AIは答えたのに、それがIssueに届いていない」状態です。

さらに別の実行では、今度は回答が Issue ではなく、main ブランチの README に書き込まれていました。質問のつもりで書いたのに、作業として扱われたわけです。

## 解決編1:回数制限に当たらないようにする

対処は3つで、どれもGitHubのリポジトリ画面だけで直せます。iPhoneのブラウザでもできます。

1. **モデルを替える**:Settings → Secrets and variables → Actions → Variables の `LLM_MODEL` を、例えば `gemini/gemini-3.1-flash-lite` に変えます。無料枠はモデルごとに独立しているので、別のモデルにするだけで回避できることがあります。
2. **再試行を粘り強くする**:ワークフローのYAMLの `env:` に次の行を足します。待ち時間を、60秒以上にして毎分の枠がリセットされるのを待ちます。
3. **作業量を減らす**:Variables に `OPENHANDS_MAX_ITER` を足し(未設定なら 20)、Issueの依頼を「index.htmlを1つ作る」のように小さくします。

```yaml
    env:
      LLM_NUM_RETRIES: "8"
      LLM_RETRY_MIN_WAIT: "60"
      LLM_RETRY_MAX_WAIT: "120"
      LLM_RETRY_MULTIPLIER: "1"
```

注意:2の環境変数名はOpenHandsの設定名から推定したもので、動作は確認できていません。効いていないときはログで設定値を確認してください。また、問題編3の実行では429は出ていなかったので、この対処だけでは「回答が届かない」は直りません。

## 解決編2:回答を読み取れなかった原因

原因は、回答を取り出すYAMLのコードが、実際の記録の形と合っていなかったことでした。コードは各イベントの `source` が `agent` のものだけを探していましたが、OpenHands 0.62.0 の output.jsonl には `source` という項目がありませんでした。そのため全イベントが対象外になり、回答が空と判定されていました。

回答は最後の `finish` イベントの `final_thought` に入っていました。分かったのは、ログのページから resolver-output（Artifacts）をダウンロードして中身を見たからです。修正は、`source` で絞ることをやめて `action` だけで判定することです。

```python
# AIの最終的な回答(質問への答え)を取り出します。
for ev in reversed(hist):
    if ev.get('action') == 'finish':
        text = (ev.get('final_thought') or (ev.get('args') or {}).get('final_thought') or '').strip()
    elif ev.get('action') == 'message' and ev.get('source') != 'user':
        text = (ev.get('content') or (ev.get('args') or {}).get('content') or '').strip()
    else:
        continue
    if text:
        res['answer'] = text[:3000]
        break
```

教訓は、「形式を確認せずに仕様を想像してコードを書かない」ことです。ログを Artifacts で保存しておく設定にしていたおかげで、後から中身を調べられました。

## 解決編3:質問と作業をAIに区別させる

READMEに書かれたのは、「表にして」という依頼をAIが「READMEを直す作業」と解釈したためです。変更があると成功と判定され、YAMLは「mainに直接反映」の分岐に入ります。この分岐はコミットの報告だけを書く作りだったので、回答は使われませんでした。

対策は2つです。

1. **Issueの書き方で指定する(すぐ効く)**:「READMEなどのファイルは変更せず、回答はこのIssueへのコメントで書いてください」と本文に足します。
2. **リポジトリのルールを置く(根本対処)**:`.openhands/microagents/repo.md` を作り、質問のときはファイルを変更しないよう書きます。バージョン0.62.0でこの場所が読まれることは、実際には確認できていません。

```markdown
---
name: repo
type: repo
version: 1.0.0
agent: CodeActAgent
---

# このリポジトリでの作業ルール

- Issueが質問・調査・比較・説明の依頼のときは、ファイルを一切変更しないでください。
- その場合は、回答を日本語で `finish` の `final_thought` に書いて終了してください。
- README.md やその他のファイルには、Issueで明示的に頼まれたときだけ書き込んでください。
- 現在使っているモデルは、Issueに書かれていなければ推測せず「不明」と答えてください。
```

もう一点、AIは自分のモデル名を知りません。今回の回答では「Gemini 1.5 Pro / Flash」と書かれていましたが、実際は gemini-3.5-flash-lite でした。`LLM_MODEL` という設定名から推測しただけです。モデルに関する質問は、現在のモデル名をIssueに書いておくと、間違ったモデル名を答えられることを防げます。

さらに、成功時のコメントにもAIの最後のまとめを載せるようにYAMLを直すと、コミット報告だけで終わることを避けられます。

## まとめ:学んだこと3点

1. **エラー文は、貼って初めて原因が分かる**:「変更なし」という結果だけでは、回数制限・読み取り失敗・解釈の違いのどれか判断できませんでした。ログと output.jsonl を見て初めて分かりました。
2. **無料枠は毎分の回数を気にする**:AIエージェントはモデルを何度も呼ぶので、毎分15回の上限に当たりやすいです。モデルを替える・待ちを長くする・依頼を小さくするのが基本です。
3. **質問と作業を区別して伝える**:AIは依頼を「ファイルを変える作業」と受け取りがちです。質問なら「ファイルは変更せず、Issueにコメントで答えて」と書くことです。

コードと設定は、どれも自分で確認したものと、推測したものを分けて記録しておくと、あとで見返すときに助かります。
